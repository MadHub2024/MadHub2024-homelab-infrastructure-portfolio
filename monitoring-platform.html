Layered Monitoring and Observability Platform

Building a multi-tool monitoring architecture that combines service availability, host metrics, container telemetry, network visibility, and DNS analytics across a segmented homelab.

Grafana Prometheus Uptime Kuma LibreNMS cAdvisor Node Exporter Technitium DNS

Executive summary

A single monitoring tool could not provide complete visibility into service availability, Linux host health, Docker container behavior, network-device state, and DNS activity. The environment therefore adopted a layered monitoring design in which each platform owns a specific class of telemetry.

Outcome: The monitoring stack provides operational visibility across more than 20 self-hosted services, two Linux infrastructure servers, Docker workloads, DNS services, and a network segmented into more than seven logical zones.

Business problem

Service availability alone did not explain host pressure, container behavior, DNS failures, or network-device health. The environment needed correlated visibility across multiple operational layers so incidents could be scoped and diagnosed with evidence.

Success criteria

  • Monitor critical application endpoints and response behavior.
  • Collect Linux host and Docker container resource metrics.
  • Add network-device and SNMP-oriented visibility.
  • Correlate DNS, host, container, and application evidence during troubleshooting.
  • Publish sanitized dashboard evidence without exposing sensitive infrastructure details.

Problem

  • A service could be reachable while its host was resource constrained.
  • A container could be running while the application endpoint was unavailable.
  • Network-device issues required SNMP-oriented visibility rather than application metrics.
  • DNS failures needed query-level evidence separate from web-service monitoring.
  • Troubleshooting required correlation across hosts, containers, applications, and network paths.

Architecture

  1. Uptime Kuma Performs endpoint and availability checks for critical internal services and records status history and response time.
  2. Prometheus Collects time-series metrics from host and container exporters.
  3. Grafana Presents operational dashboards for resource use, service health, and infrastructure trends.
  4. Node Exporter Exposes Linux CPU, memory, filesystem, load, and network metrics.
  5. cAdvisor Provides container-level CPU, memory, filesystem, and network telemetry.
  6. LibreNMS Supports SNMP-based network-device discovery, health monitoring, and topology-oriented visibility.
  7. Technitium DNS and AdGuard Home Provide query statistics, failure evidence, filtering data, and resolver-path visibility.

Implementation sequence

  1. Service inventoryIdentified critical applications, hosts, containers, DNS services, and network devices.
  2. Availability monitoringAdded endpoint checks in Uptime Kuma for infrastructure applications.
  3. Exporter deploymentDeployed Node Exporter and cAdvisor to expose host and container metrics.
  4. Metrics collectionConfigured Prometheus to collect time-series telemetry from available exporters.
  5. Dashboard creationBuilt Grafana views for infrastructure overview, resource usage, and service telemetry.
  6. Network visibilityDeployed the LibreNMS application, dispatcher, Redis, and MariaDB stack for SNMP monitoring.
  7. DNS correlationUsed Technitium and AdGuard dashboards to compare service symptoms with resolver activity.
  8. Portfolio evidenceSanitized screenshots before publishing dashboard evidence publicly.

Monitoring responsibilities

Availability

Uptime Kuma answers the immediate operational question: can the service endpoint be reached, and how quickly is it responding?

Host health

Node Exporter provides evidence about CPU, memory, load, storage, filesystem utilization, and network activity on Linux hosts.

Container behavior

cAdvisor separates container resource consumption from overall host utilization, making it easier to identify workload-specific pressure.

Network state

LibreNMS adds device-centric visibility through SNMP, interface status, health metrics, and network topology.

DNS behavior

Technitium DNS and AdGuard Home provide evidence for query volume, client activity, cache behavior, blocked requests, and resolver failures.

Operational workflow

Monitoring is used as a diagnostic sequence rather than a collection of unrelated dashboards:

  1. DetectUse Uptime Kuma or dashboard status to identify an unavailable or degraded service.
  2. ScopeDetermine whether the symptom affects one endpoint, one container, one host, or multiple network segments.
  3. CorrelateCompare Grafana host and container metrics with application logs and DNS activity.
  4. Validate the pathTest DNS, TCP reachability, HTTP readiness, and routing independently.
  5. RecoverApply the smallest corrective action supported by the available evidence.
  6. VerifyConfirm endpoint health, metrics recovery, and normal query or response behavior.
  7. DocumentRecord the cause, validation steps, and preventive improvements.

Operational improvements

  • Separated availability checks from resource and network telemetry.
  • Added host-level and container-level evidence to troubleshooting.
  • Centralized dashboards for faster cross-system correlation.
  • Used DNS analytics to distinguish resolver failures from application failures.
  • Documented repeatable validation commands for service recovery.
  • Published sanitized evidence without exposing production-sensitive details.

Lessons learned

  • A running container is not proof that an application is ready.
  • Endpoint monitoring and infrastructure metrics answer different questions.
  • DNS should be validated early in every service investigation.
  • Monitoring architecture should match the layers of the system being operated.
  • Dashboard screenshots require the same sanitization discipline as configuration files.

Lessons learned

  • No single monitoring tool provides complete visibility across applications, hosts, containers, DNS, and network devices.
  • Availability monitoring and infrastructure telemetry answer different operational questions and should be correlated.
  • Dashboards are most useful when they prioritize actionable signals instead of every available metric.
  • Monitoring evidence should be paired with repeatable validation commands and documented response procedures.

What I would do differently

I would define service-level indicators and alert thresholds before building dashboards, then centralize notifications and logs earlier in the deployment. I would also automate configuration backups and create runbooks that map each alert to specific diagnostic steps.
