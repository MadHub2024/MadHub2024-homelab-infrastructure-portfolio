Case Study 03 · Incident Recovery

Vaultwarden Recovery and Service Hardening

Recovering a missing Vaultwarden container while protecting the persistent SQLite database, validating service readiness, and improving the update and rollback workflow.

Linux Docker Compose SQLite Vaultwarden Caddy Bash Argon2

Executive summary

The Vaultwarden container was absent after an update attempt even though its image, Docker network, Compose project, and persistent data directory remained available. Because the service held administrative credentials for the homelab, the priority was to restore availability without damaging or replacing the encrypted vault database.

Outcome: Vaultwarden returned to service with the existing database intact, SQLite integrity verified, Docker health confirmed, and the local application endpoint returning HTTP 200.

Business problem

Vaultwarden stored administrative credentials used across the homelab. The missing application container made those credentials temporarily unavailable, creating an operational dependency that had to be restored without damaging the persistent encrypted database.

Success criteria

  • Protect the existing Vaultwarden data before making changes.
  • Verify that the SQLite database was structurally sound.
  • Recreate the application without replacing the persistent vault.
  • Confirm container health and an HTTP 200 application response.
  • Document a repeatable backup, recovery, and validation process.

What broke and why it mattered

The application container was no longer present, so the Vaultwarden web service could not accept requests. The persistent data directory remained on disk, but recreating the container without first validating that data could have increased the risk of compounding the incident.

  • The password-management application was unavailable.
  • The reverse proxy had no healthy backend service to reach.
  • Administrative credentials were temporarily inaccessible.
  • Database integrity had to be established before redeployment.

Recovery timeline

  1. DetectionConfirmed that no Vaultwarden container existed.
  2. Configuration discoveryLocated the Compose project, image definition, port mapping, environment settings, and persistent bind mount.
  3. Data protectionCreated a timestamped copy of the complete Vaultwarden data directory before starting recovery work.
  4. Database validationRan SQLite PRAGMA integrity_check; the database returned ok.
  5. Service recreationRecreated the application with docker compose up -d.
  6. Runtime validationReviewed startup logs and confirmed that the container reached a healthy state.
  7. Endpoint validationRequested the local endpoint on port 8087 and received HTTP/1.1 200 OK.

Diagnosis and evidence

Container-state analysis

Docker inspection confirmed that the service container itself was absent. This separated the application-runtime failure from the persistent storage layer.

Compose and volume validation

The Compose file showed that Vaultwarden stored application data through a bind mount:

./data:/data

Backup before modification

cp -a data "data-backup-$(date +%Y%m%d-%H%M%S)"

SQLite integrity validation

sqlite3 data/db.sqlite3 'PRAGMA integrity_check;'

The command returned:

ok

This was the key recovery decision point. It provided evidence that the persistent database was structurally sound and that service recreation could proceed without restoring an older backup.

Root cause

The outage was caused by the application container being absent after an update attempt, not by database corruption. A second issue was identified in the recovery workflow: an early readiness check treated Docker's delayed health transition as an application failure even though the Rocket web server was already responding.

Recovery and verification

docker compose up -d
docker compose ps
curl -I http://127.0.0.1:8087/
  • The container reported running and healthy.
  • Startup logs identified Vaultwarden version 1.37.0.
  • The local endpoint returned HTTP 200 OK.
  • The existing SQLite database remained intact.

Preventive changes

  • Created a timestamped data backup before every update or recovery.
  • Added SQLite integrity validation before service recreation.
  • Changed readiness validation to test the actual HTTP endpoint.
  • Preserved rollback information and Compose backups.
  • Documented the complete recovery sequence.
  • Identified the plaintext administrative-token warning for Argon2 hardening.

Lessons learned

  • Persistent application data must be validated independently from container state.
  • Creating a backup before recovery changes reduced the risk of turning an outage into data loss.
  • A running container is not sufficient evidence of application readiness; endpoint and database checks are both required.
  • Recovery procedures are stronger when rollback points, validation commands, and expected results are documented in advance.

What I would do differently

I would automate pre-upgrade backups, SQLite integrity checks, and post-deployment HTTP validation in a repeatable maintenance script. I would also store the administrative token as an Argon2 hash from the beginning and add a monitored backup-verification schedule.
