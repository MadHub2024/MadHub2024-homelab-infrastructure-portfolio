Case study 03

Vaultwarden Recovery and Hardening

Recovering a missing container safely while preserving encrypted vault data and improving the update workflow.

Docker ComposeSQLiteCaddyTLSBashArgon2

Incident

The Vaultwarden container was absent after an update attempt, while the image and Docker network still existed. The priority was to restore the service without risking the persistent password database.

Data validation

I located the Compose project and confirmed the bind mount:

/home/denalidennyb/vaultwarden/data → /data

Before deployment, I created a timestamped backup and ran SQLite integrity validation:

sudo cp -a data "data-backup-$(date +%Y%m%d-%H%M%S)"
sudo sqlite3 data/db.sqlite3 'PRAGMA integrity_check;'

Service recovery

I validated the Compose configuration, recreated the container, monitored application logs, confirmed Docker health, and tested the local HTTP endpoint before testing the Caddy hostname.

Security hardening

The update also replaced a plaintext administrative token with an Argon2 PHC hash. A Bash workflow was built to back up the Compose file, validate syntax, recreate the service, test HTTP readiness, detect plaintext-token warnings, and preserve rollback information.

Root-cause reasoning

An initial script treated Docker's delayed health transition as an application failure even though Rocket was already serving HTTP. The readiness test was redesigned to check the actual service endpoint for HTTP 200 instead of relying solely on the container health timestamp.

Result

Vaultwarden returned to service with an intact database, verified backups, secure administration, valid internal TLS, and a repeatable update procedure.
